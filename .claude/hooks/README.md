# フック — ガード 3 層（Stop 検証・操作ガード・PR ガード）

このリポに配られているハーネスの説明。正本は loop-engineering の `templates/`（配布物は
無改変のコピーで、ai-workbench の harness.tsv が同期を毎日検査する）。設計の思想は
loop-engineering の PHILOSOPHY.md §1（お願いは手紙の中、仕組みは手紙の外）・§4（検証して
いない場所を緑と読まない）・§6（ガード）。

| 層 | ファイル | 効く条件 | 何を止めるか |
|---|---|---|---|
| Stop 検証 | `stop-validate-links.sh` | 常時 | リンク切れを残したままセッションを終われない（差し戻し 5 回上限） |
| Stop 検証 | `stop-validate-merge-markers.sh` | 常時 | 衝突マーカー（マージの解消し忘れ）を残したまま終われない（同上） |
| 操作ガード | `guard-branch.sh` | 既定は常時。隣に `guard-branch.scope`（1 行 `ax-only`）があるリポだけ ax セッション限定 | main / master への直接コミット・push（「PR まで自動・マージは人間」の機械担保） |
| PR ガード | `guard-pr.sh` | 常時 | `--body` 直書き・必須 6 節の欠け・check-goal 出力なし・土台検証不合格・origin/main 未追随のままの PR 作成 / マージ |

ループの終了判定は `check-goal.sh`（いまの獲物の「成功の定義」を機械判定する）。
**Stop フックには載せない** — 未完成のうちは当然未達で無限差し戻しになるため。
`check-goal.sh` は同じディレクトリの `validate-*.sh` を全部呼ぶので、リポ固有の検査は
`validate-<名前>.sh` を 1 本置けば土台に自動で載る。

Stop に載るのは汎用 2 本（links / merge-markers）だけ。Claude 版・Cursor 版とも同じ
2 本で、リポ固有の重い検査は Stop に載せない（毎ターン走ると日常が遅くなる。リポ固有の
検査は check-goal と guard-pr の土台検証で走る）。

## 手で確認したいとき

```bash
.claude/hooks/validate-links.sh
.claude/hooks/validate-merge-markers.sh
.claude/hooks/check-goal.sh
```

## PR ガードに拒否されたら（差し戻しであって、終わりではない）

`guard-pr.sh` の拒否は **「型を直して出し直せ」という差し戻し**。stderr に日本語で
直し方が出る。読んで直し、**同じコマンドを再実行する**。

- 本文の型はこのリポの `.claude/pr-body.md`。複製して埋める:
  `cp .claude/pr-body.md /tmp/pr-body.md`
- 「ゴールの計測結果」には `.claude/hooks/check-goal.sh` の出力を**そのまま**貼る（要約しない）
- 該当が無い節は消さずに「なし」と書く

やってはいけないこと:

- **手動の PR 作成 URL に逃げる**（`https://github.com/.../compare/...` を人間に渡して終わりにする）
- **PR ができていないのに TODO を完了にする**
- ガードを外す・緩める（門番が正しく仕事をしている。直すのは PR 本文の側）

## 「フックに拒否された」には層が 2 つある（取り違えると対策を誤る）

同じ「拒否された」に見えて、直し方がまったく違う。**まず stderr の中身を見て切り分ける。**

| 層 | 何が止まるか | 拒否の中身 | 直し方 |
|---|---|---|---|
| **リポの門番**（このディレクトリの `guard-pr.sh` / `guard-branch.sh`） | `gh pr create` / `gh pr merge` / `git commit` / `git push` | **日本語で直し方が出る**（`--body-file` にせよ・6 節が足りない・作業ブランチに移れ 等） | 指示どおり型を直して**再実行する**。通るまで未完了 |
| **AI 製品側**（Cursor Settings > Hooks / Auto-review など） | `gh issue create` のように**リポの門番の対象外**のコマンドも含む | **定型文だけ**（"Command execution was blocked by a hook." など）。直し方が書かれていない | リポ側では直せない。本文をファイルに書いて**人間のターミナルで同じコマンドを叩く**。製品設定の変更は別判断 |

切り分けの目印:

- **日本語の直し方が出た → リポの門番**。設計どおりの拒否。型を直して再試行する
- **定型文だけで直し方が無い → 製品側**。しかも `gh issue create` はどのリポフックにも当たらない
  （`guard-pr.sh` が見るのは `gh pr create` と `gh pr merge` だけ、`guard-branch.sh` が見るのは
  `git commit` と `git push` だけ）。本文の不備ではないので、本文を直しても通らない
- 手元のターミナルで同じコマンドが通るなら、リポの門番ではない（門番は人間のターミナル
  操作には効かない — AI のツール呼び出しだけを見ている）

製品側で止まったときは、**「起票できなかった」で終わらせない**。本文ファイルのパスと
実行すべきコマンドを人間に渡して引き継ぐ。

## 設計の原則

- **合否判定に AI を使わない**: 作業した本人に採点させず、grep / find の実測だけで判定する
- **終了コードが返事**: 0 = 通す / 2 = 差し戻す。お願い（プロンプト）ではなく仕組みで守る
- **やり直し上限 5 回**: 無限ループ防止。超えたら人間に引き渡す
- **判定できないときは通す**（フェイルオープン）: 門番が壊れて全作業が止まる方が害が大きい。
  ただし `guard-branch` の発火モードだけは既定を厳しい側（無条件）に倒す — 置き忘れが
  「うるさいが見える失敗」になる向きに倒すため
- 誤発火して日常作業を妨げるようなら、**フックを外すのではなく検証条件を狭めてから再開する**
